# Как я понимаю команды и настройки

## Что я нахожу в package.json

Я читаю этот файл как паспорт проекта и меню команд. name обозначает пакет, version — версию основы API 0.1.0. Объяснённую копию я различаю веткой и документами, а не выдуманной новой возможностью API. private true запрещает случайную публикацию пакета в npm; публичность репозитория GitHub от этого не меняется. type module включает используемый синтаксис import. engines задаёт диапазон Node 24, для которого я подготовил стенд.

| Поле | Как я его использую |
| --- | --- |
| scripts | Я сопоставляю короткое имя команды с реальным файлом запуска |
| dependencies | Я устанавливаю GraphQL и Yoga для работы сервера |
| devDependencies | Я устанавливаю Bruno CLI и fflate для проверок и архива |
| overrides | Я закрепляю исправленные версии некоторых вложенных библиотек Bruno |

Я не заменяю версии случайным latest: это изменит состав установки и может сломать совместимость. В package-lock я сохраняю точные версии всего дерева, адреса загрузки и integrity. Для чистой установки я использую npm ci; если package.json расходится с lock, я ожидаю отказ вместо тихого выбора нового дерева.

## Какие команды я выполняю

| Команда | Что я запускаю | Что я получаю |
| --- | --- | --- |
| npm ci --ignore-scripts --no-fund | Я устанавливаю закреплённые пакеты | Папку node_modules; не запускаю install-скрипты зависимостей |
| npm start | Я запускаю src/server.js | Стенд на 127.0.0.1:8767 до Ctrl+C |
| npm start -- --training-bug | Я передаю флаг server.js | Тот же стенд с намеренным дефектом прав |
| npm run demo | Я запускаю scripts/run-collection.js | Временный сервер, полный прогон, три отчёта и завершение сервера |
| npm test | Я запускаю node:test | 8 дополнительных API-проверок реализации |
| npm run check | Я запускаю scripts/ci.js | API, эталон, обнаружение дефекта и source ZIP |
| npm run package | Я запускаю scripts/package-release.js | Только архив и SHA256SUMS без повторного прогона API |

`--` после npm start я использую, чтобы передать следующий аргумент самой программе. В обычном старте сервер не завершается сразу: я ожидаю, что терминал останется занят им. В demo я, наоборот, ожидаю завершения команды. Для установки мне нужен доступ к реестру npm; дальнейшие запросы к стенду выполняются локально.

## Как я читаю файл запроса Bruno

| Блок .bru | Что я в нём задаю |
| --- | --- |
| meta | Я задаю название, тип graphql и порядок seq |
| post | Я задаю URL, GraphQL-тело и отсутствие встроенной схемы auth клиента |
| headers | Я задаю формат тела, формат ответа и демо-персону |
| body:graphql | Я пишу саму query или mutation |
| body:graphql:vars | Я задаю JSON переменных |
| assert | Я перечисляю выражения, операторы и ожидаемые значения |
| docs | Я читаю объяснение; этот блок не отправляется API |

auth none не отменяет мой учебный контроль ролей: X-Demo-Actor я передаю обычным заголовком. В Local.bru я храню baseUrl. Двойные фигурные скобки в `{{baseUrl}}` обозначают подстановку Bruno; это не переменная GraphQL с долларом. Я выбираю окружение Local, иначе клиент может не собрать нужный адрес.

Я начинаю с GUI, потому что он редактирует корректный формат файла за меня. В JSON и bruno.json я не вставляю комментарии: JSON их не поддерживает. Я держу их объяснение в этом уроке.

## Как я различаю отчёты

В HTML я читаю результаты глазами. JSON я использую для программного анализа; поэтому ci.js может найти результат запроса 15 и конкретный отказ Assert. JUnit XML я оставил для инструментов, принимающих такой формат. Слово Tests 0/0 в выводе Bruno не означает, что проверок нет: мой low-code набор использует **Assertions 83/83**, а не JavaScript-вкладку Tests.

Файл training-bug появляется отдельно от regression. В нём я ожидаю красные строки. Общий check считается успешным, если исправный стенд зелёный, а нужный дефект обнаружен. Я не объявляю любое падение доказательством качества: проверяю конкретный запрещённый результат.

## Как я понимаю CI

В .github/workflows/check.yml я вижу две проверки одной команды: на Linux и Windows. Workflow запускается на main, codex-ветках и pull request. Полные SHA действий закрепляют использованные версии checkout и setup-node. Runner сначала устанавливает Node и зависимости, затем выполняет audit и check.

Отдельный release job зависит от успешных проверок и разрешён только для push main исходного репозитория. Поэтому в моей объяснённой ветке я ожидаю **checks success, release skipped**. Я сохранил публикационный скрипт как часть полного проекта, но не перемещаю стабильный тег ради учебных комментариев. Для собственного нового репозитория я сначала осознанно меняю настройки публикации и версию; для упражнений это не требуется.

## Как я создаю безопасный архив

Я перечисляю разрешённые файлы в SOURCE_FILES.txt. Упаковщик не обходит всю папку подряд, поэтому случайная база или отчёт не должны попасть в архив только из-за соседства с кодом. .gitignore помогает Git не предлагать лишнее, а SOURCE_FILES отдельно задаёт поставку. Это два разных контроля.

Я дополнительно отклоняю некоторые признаки секретов, контактов и личных путей. Такой фильтр не находит любой возможный секрет; я всё равно просматриваю состав. SHA256SUMS позволяет сверить байты архива после копирования. Контрольная сумма подтверждает совпадение с ожидаемым файлом, а не качество бизнес-логики.

## Как я пользуюсь IDE

В VS Code я открываю именно папку объяснённой копии. Через **Terminal → Run Task** я нахожу npm start, demo и check из .vscode/tasks.json. Через Run and Debug я могу запустить сервер с точкой остановки. Для первых упражнений это необязательно: Bruno уже даёт нужный интерфейс.

Я не держу одновременно два обычных сервера основы и копии на порту 8767. Я останавливаю один через Ctrl+C. Автоматический demo использует свободный порт и не требует менять Local. Если я всё же меняю постоянный порт в server.js, я одновременно меняю baseUrl Local.bru: изменение только одного конца разрывает соединение.
