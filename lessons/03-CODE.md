# Как я читаю код без спешки

## Зачем я разделил файлы

Я не пытаюсь сразу понять весь сервер. Я разделяю три вопроса: **что можно запросить**, **по каким правилам я отвечаю**, **как я запускаю программу**. На первый отвечает schema.graphql, на второй app.js, на третий server.js. Если я хочу поменять ограничение title, я иду в app.js; если хочу лишь запросить существующее поле, мне достаточно Bruno.

## Какие записи JavaScript мне нужны

| Запись | Как я её читаю в этом проекте |
| --- | --- |
| import | Я беру функцию из другого файла или библиотеки |
| const | Я задаю имя, которое не буду переприсваивать; содержимое объекта при этом может меняться |
| let | Я задаю переменную, которую могу переприсвоить, например nextId |
| `{ id: 'T-1001' }` | Я создаю объект со свойством id |
| `[a, b]` | Я создаю массив из двух элементов |
| `({ id })` в параметрах | Я извлекаю свойство id из переданного объекта |
| `() => value` | Я записываю короткую функцию, возвращающую value |
| if | Я выбираю действие по условию |
| return | Я заканчиваю функцию и отдаю результат |
| throw | Я прерываю нормальный путь ошибкой; GraphQL оформляет ожидаемый отказ поля |
| async / await | Я описываю ожидание результата операции, например сетевого запроса |
| try / finally | Я выполняю очистку даже после исключения внутри try |

Я не считаю const защитой от изменения объекта. Именно поэтому `ticket.status = input.status` работает: я меняю свойство объекта, а не присваиваю переменной ticket другой объект. Object.freeze(users) в начале защищает верхний объект users от добавления и замены его свойств; вложенные записи он глубоко не замораживает. Я нигде не меняю эти записи.

## Как я храню данные

В users я вижу три заранее заданных объекта. Ключ customer-a совпадает со значением заголовка. В tickets я использую Map: ключом служит ID, значением — объект обращения. `tickets.get('T-1001')` возвращает запись, `tickets.set(id, ticket)` сохраняет её, `tickets.values()` позволяет перебрать все записи.

Я создаю Map внутри createApp. Это решение даёт каждому экземпляру собственные данные. Если бы я вынес один изменяемый Map за пределы createApp, два тестовых сервера начали бы делить состояние. nextId находится в той же области: reset возвращает его к 2001, а успешное создание увеличивает на единицу.

Я не записываю обращения на диск. Пока процесс жив, Map сохраняется между HTTP-запросами. После остановки процесса его содержимое исчезает. Сам код остаётся на диске; данные в Map и исходный файл app.js — разные вещи.

## Как я выбираю персону

В настройке context я читаю request.headers.get('x-demo-actor'). Затем через Object.hasOwn проверяю, есть ли такой собственный ключ в users. Для известного ключа я кладу объект персоны в context.actor, для неизвестного — null. Это контекст только текущего запроса, а не глобально выбранный пользователь всех клиентов.

Вспомогательная actor(context) требует известную персону. staff(context) сначала вызывает actor, затем требует роль STAFF. Я переиспользую этот контроль для reset, смены статуса и внутренней заметки. Проверка права в одном месте не означает, что любые новые поля автоматически защищены: при добавлении закрытого действия я сам обязан вызвать нужный контроль.

## Как один запрос проходит через код

Для 03-own-ticket я прослеживаю весь путь:

1. Я нажимаю Send. Bruno собирает HTTP POST, заголовок роли, GraphQL и Variables.
2. Node принимает соединение и передаёт запрос Yoga.
3. Yoga использует схему: проверяет документ и входные значения. Неправильный тип не доходит до моего поиска записи.
4. Для корректного запроса я получаю context.actor customer-a.
5. Yoga вызывает Query.ticket с аргументом id T-1001.
6. Я проверяю персону, нахожу объект в Map и сверяю владельца.
7. Для вложенного owner Yoga использует Ticket.owner: по ownerId я возвращаю объект DemoUser.
8. Я получаю JSON только с выбранными полями. Bruno выполняет Assert.

В резолвере `(_, { id }, context)` первым параметром является родительский объект. Для корневого поиска он мне не нужен, поэтому я назвал его _. Во втором параметре я получаю аргументы поля, а третьим — контекст. В Ticket.owner первый параметр уже нужен: это найденный ticket, из которого я беру ownerId.

## Как я читаю фильтр списка

В цепочке `values → filter → slice` я сначала получаю все записи, затем оставляю доступные текущей персоне, затем применяю status, затем беру первые first элементов. Сотрудник видит все записи, клиент — только свои. Если status не передан, я не фильтрую по статусу.

Порядок имеет значение. Если я сначала возьму один произвольный элемент, а затем отфильтрую его по владельцу, я могу получить пустой результат, хотя подходящие записи существуют дальше. Поэтому я ограничиваю уже отфильтрованный список. Здесь нет сортировки по дате: Map сохраняет порядок добавления. Я не называю это полноценной пагинацией.

## Как я создаю обращение

В createTicket я читаю input, проверяю персону, убираю крайние пробелы title и проверяю длины. При отказе я сразу возвращаю rejected: ticket null и массив userErrors. Счётчик в этот момент ещё не увеличен.

При успехе я собираю новый объект, задаю OPEN и ownerId текущей персоны. `nextId++` подставляет текущее число, затем увеличивает счётчик. После tickets.set я возвращаю ticket и пустой userErrors. Ровно поэтому невалидная попытка не должна «съесть» номер, а успешная — должна изменить последующее чтение.

## Как я меняю статус

Сначала я требую staff. В режиме trainingBug я намеренно заменяю это требование на простую проверку любой известной персоны. Так клиент получает запрещённое право; это контролируемая учебная ошибка.

После контроля я ищу запись. Для неизвестного ID возвращаю TICKET_NOT_FOUND. Таблица transitions задаёт по одному следующему состоянию для OPEN и IN_PROGRESS. У RESOLVED ключа нет, поэтому любой следующий статус будет отклонён. Только после проверки я присваиваю ticket.status. Я отдельно проверяю чтением, что отказ до этой строки не изменил запись.

## Как я получаю частичный ответ

Ticket.internalNote проверяет staff независимо от Query.ticket. Поэтому клиент может получить разрешённый объект, но не заметку. В схеме заметка допускает null; GraphQL может вернуть остальные выбранные поля вместе с ошибкой этой заметки. Я читаю path, чтобы узнать, какое поле отказало. Я не скрываю всё обращение просто потому, что внутри есть одно закрытое поле.

## Зачем нужны служебные скрипты

Я начинаю их изучение после app.js. run-collection поднимает сервер на свободном порту, запускает реальный Bruno CLI, читает отчёт и закрывает сервер. ci.js проверяет эталон и чувствительность к учебному дефекту. package-release отбирает исходники по списку и формирует архив. publish-release работает только в ограниченном контексте GitHub CI и не требуется для отправки запросов.

Я не начинаю самостоятельную переделку с удаления этих файлов: они помогают мне понять, что я сохранил рабочее поведение. В каждом я оставил комментарии рядом с ключевыми решениями; дополнительные параметры я разбираю в уроке 4.
