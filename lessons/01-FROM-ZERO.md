# Как я понимаю API с нуля

## Что я называю сервером и клиентом

Я представляю стойку службы поддержки. Клиент формулирует просьбу, сотрудник проверяет правила и выдаёт результат. В стенде Bruno играет роль отправителя, а запущенный Node-процесс — роль получателя. Набор правил и способов обратиться к нему я называю API. Я использую аналогию только для начала: реальные запросы имеют точную структуру и не понимают произвольный человеческий текст.

Я запускаю сервер командой npm start. Пока процесс работает, он принимает запросы по локальному адресу. Закрытый терминал означает остановленный сервер. Клиент Bruno работает отдельно и сам не заменяет сервер.

Я читаю адрес `http://127.0.0.1:8767/graphql` по частям:

| Часть | Как я её понимаю |
| --- | --- |
| http | Я передаю запрос по HTTP; здесь без TLS |
| 127.0.0.1 | Я обращаюсь к этой же машине |
| 8767 | Я выбираю порт — номер, по которому процесс принимает соединения |
| /graphql | Я выбираю путь обработчика GraphQL |

Я не отправляю учебные обращения на внешний сервис. Установка библиотек из npm и публикация исходников на GitHub — отдельные сетевые действия.

## Что я отправляю через HTTP

Я использую POST даже для операции чтения query. Поэтому я не делаю вывод «POST обязательно создаёт запись». Действие я определяю по операции и контракту API.

Я отправляю заголовки — дополнительные сведения о запросе. Content-Type application/json говорит о формате тела. Accept application/graphql-response+json указывает ожидаемый формат ответа и связан с правилами HTTP-кодов выбранного сервера. X-Demo-Actor customer-a выбирает вымышленную персону. Последний заголовок не является паролем: любой локальный клиент может заменить его на staff. Я не считаю такую модель готовой аутентификацией.

Тело запроса содержит GraphQL-текст и объект variables. Bruno собирает HTTP-представление за меня. Я редактирую Query и Variables во вкладках.

## Как я читаю JSON

Я воспринимаю JSON как текстовую запись данных. В объекте я вижу пары ключ → значение; в массиве — список элементов по порядку.

```json
{
  "id": "T-1001",
  "title": "Не открывается учебный отчёт",
  "status": "OPEN"
}
```

Я различаю строку `"1"`, число `1`, boolean `true`, значение `null`, пустой массив `[]` и пустой объект `{}`. Они не взаимозаменяемы. В JSON я использую двойные кавычки, не добавляю комментарии и запятую после последнего поля.

null означает присутствующее поле без значения. Если ключа вообще нет, я не вижу его в объекте. В Assert я проверяю первое через isNull, второе через isUndefined. Самого слова undefined в JSON нет: так клиент описывает отсутствие свойства.

## Что я делаю с GraphQL

Я прошу сервер вернуть выбранные поля:

```graphql
query Ticket($id: ID!) {
  ticket(id: $id) {
    id
    title
    owner {
      id
    }
  }
}
```

Я читаю это так: «выполни чтение с именем Ticket, прими обязательный id, найди ticket и верни его id, title и id владельца». Имя операции Ticket я выбрал для удобства; оно не обязано совпадать с именем типа или поля. Имя поля ticket должно существовать в схеме. Вложенный owner означает выбор полей внутри другого объекта.

В Variables я задаю:

```json
{"id": "T-1001"}
```

Я объявляю переменную как $id в GraphQL, а в JSON пишу ключ id без доллара. В `ticket(id: $id)` слева я вижу имя аргумента поля, справа — значение из переменной. Я меняю ID отдельно от структуры запроса.

Я использую mutation для создания и смены статуса. Ответ mutation тоже содержит выбранные поля. Если я не запросил title, его отсутствие в ответе само по себе не означает, что он не сохранился.

## Как я читаю схему

Я использую схему как меню допустимых операций. type Ticket описывает возвращаемый объект, input CreateTicketInput — вход создания. String означает строку, ID — идентификатор, Int — целое число. Через enum я перечисляю допустимые статусы.

Я читаю String! как запрет null, а не пустой строки. Поэтому title с пробелами проходит проверку типа, но отклоняется бизнес-правилом. Для `[UserError!]!` я ожидаю массив без null-элементов; он может быть пустым. Типы я сверяю с [официальным объяснением схем](https://graphql.org/learn/schema/).

## Почему HTTP 200 не заканчивает проверку

Я отдельно читаю транспортный результат и содержимое GraphQL. Разрешённая часть объекта может вернуться вместе с errors. Я проверяю data, errors и path ошибки. Эту модель я сверяю с [официальным описанием ответа](https://graphql.org/learn/response/), а ожидания своего API — с TEST_PLAN.

| Что я отправил | Где я ищу результат |
| --- | --- |
| Неизвестное поле password или неверный тип переменной | Я ожидаю HTTP 400, errors и отсутствие data |
| Корректный запрос чужого обращения | Я ожидаю HTTP 200, null поля и FORBIDDEN в errors |
| Корректное создание с пустым title | Я ожидаю HTTP 200 и TITLE_INVALID внутри data.createTicket.userErrors |

Я не обобщаю HTTP 400 на каждый сервер GraphQL: здесь я закрепил стек и Accept. Я не приравниваю userErrors к встроенному errors: первое я определил в бизнес-контракте.

## Как я читаю проверку

В Assert я задаю: откуда взять факт, как сравнить и с чем сравнить. Для res.body.data.ticket.id, eq, T-1001 я ожидаю совпадение номера. Через точки я спускаюсь по вложенным объектам. Запись [0] означает первый элемент массива: нумерация начинается с нуля.

Зелёный негативный тест не означает, что запрещённое действие удалось. Я отправляю запрещённый запрос, получаю ожидаемый отказ и считаю проверку успешной. Красный тест означает расхождение факта с ожиданием; причину я ещё должен расследовать.

Я могу показать запрос, назвать роль, найти переменную и объяснить Assert. Затем я специально меняю ожидаемый ID на неверный и наблюдаю красный результат. Так я вижу, что проверка сравнивает данные, а не просто рисует зелёную отметку.
