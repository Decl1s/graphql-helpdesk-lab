# Как я проверяю контракт

Я использую три роли: `customer-a`, `customer-b`, `staff`. Это переключатели вымышленных персон. Я не проверяю реальные пароли или токены. `customer-a` владеет T-1001 и T-1003, `customer-b` — T-1002. Я разрешаю читать свои обращения; сотруднику — все и `internalNote`. Создавать может любая известная роль. Сброс и смена статуса доступны только сотруднику.

Я принимаю `title` длиной 3–80 после trim и `description` до 500 включительно. Я измеряю длину через JavaScript `String.length` (кодовые единицы UTF-16), не обещаю подсчёт визуальных символов. Я разрешаю OPEN → IN_PROGRESS → RESOLVED, запрещаю остальные переходы, в том числе повтор текущего статуса. Я ожидаю `first` от 1 до 20, по умолчанию 10; явный null отклоняю.

| Кейсы | Приоритет | Что я ожидаю |
| --- | --- | --- |
| 00, 01, 02 | P0 | Я вижу доступность, 3 исходных обращения, нужную роль |
| 03, 04 | P1 | Я читаю вложенного владельца; aliases и fragment возвращают два ожидаемых статуса |
| 05 | P1 | Я получаю один OPEN, принадлежащий клиенту А |
| 06 | P1 | Я получаю null без errors для отсутствующего ID |
| 07 | P0 | Я получаю FORBIDDEN и null при чтении чужого обращения |
| 08 | P0 | Я получаю частичные data, null внутренней заметки и точный path |
| 09, 10, 14 | P0 | Я получаю HTTP 400, errors и отсутствие data до выполнения |
| 11, 12 | P0 | Я получаю T-2001, title после trim, OPEN и читаю результат |
| 13 | P1 | Я получаю TITLE_INVALID в userErrors без создания ticket |
| 15 | P0 | Я получаю FORBIDDEN при смене статуса клиентом |
| 16, 17 | P0 | Я последовательно получаю IN_PROGRESS и RESOLVED |
| 18, 19 | P0 | Я получаю BAD_TRANSITION; итог остаётся RESOLVED |
| 20 | P0 | Я получаю UNAUTHENTICATED без выбранной роли |
| 21 | P1 | Я получаю BAD_USER_INPUT на first=0 |

Я дополняю коллекцию 8 API-проверками в Node: верхняя граница first, null, неизвестные роли и имена свойств прототипа, границы строк, отсутствие расходования ID после отказа, неизвестный ID mutation, запрет reset, изоляция экземпляров и контроль режима дефекта.

Я выполняю полную коллекцию в порядке seq на одном выделенном стенде. Я не подменяю намеренную HTTP/GraphQL-ошибку падением теста: негативный кейс зелёный, если ошибка соответствует контракту. Я считаю выпуск подходящим для учебной демонстрации после зелёного эталона и подтверждённого обнаружения контролируемого дефекта. Нагрузочные, реальные проверки безопасности и ручные Desktop-проверки я не считаю выполненными этим планом автоматически.
